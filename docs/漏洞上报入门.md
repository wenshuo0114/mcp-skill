# 漏洞上报入门：发现了问题，正确地告诉该负责的人

审查器只能告诉你"这里有问题"。问题**属于谁**、**该告诉谁**、**怎么说**，是另一回事。这份文档讲流程，**不讲任何复现方法**。

---

## 一、先分三种情况：问题在谁的代码里

| 情况 | 例子 | 该做什么 |
|---|---|---|
| **A. 你自己的代码/仓库/机器** | 你的项目里有硬编码密钥；你的 VPS 上有陌生定时任务 | 自己修：无害化 → 换凭据 → 写进审查报告。不需要上报任何人 |
| **B. 别人的开源项目/软件** | 你用的某个 npm 包有后门；某个编辑器插件偷读 `~/.ssh` | **协调披露**：先私下告诉维护者，给他们修的时间，再公开 |
| **C. 微软/苹果/谷歌等大厂的产品** | Windows 组件、VS Code 本体、Chrome 本体的漏洞 | 走厂商的安全响应中心（MSRC / Apple Product Security / Google VRP） |

第 A 种最常见。审查器 90% 的发现都是 A。

**判断标准**：问题出在**谁写的、谁维护的**代码里。你 `pip install` 来的包里有问题，是 B；你自己写错的配置，是 A。

---

## 二、协调披露（B 类）标准流程

"协调披露"= 先私下告诉负责的人，约定一个公开日期，让他们有时间修，再一起公开。这是行业共识（ISO/IEC 29147、CERT/CC 指南、GitHub 安全策略）。

### 第 1 步：找到私密上报渠道（不要发公开 issue）
按顺序找：
1. 仓库里的 `SECURITY.md`（通常在根目录或 `.github/`），里面写了怎么上报。
2. GitHub 仓库页 → **Security** 标签 → **Report a vulnerability**（私密 advisory，只有维护者能看）。
3. 项目官网的 `/security` 或 `/.well-known/security.txt`。
4. 维护者的邮箱（`security@域名` 优先）。
5. 都没有：先发一条**不含细节**的公开 issue："我发现了一个安全问题，想私下联系维护者，请告知渠道。"

**不要**在公开 issue、Discord、推特上贴细节。

### 第 2 步：写报告（只写事实）
```
标题：[安全] <组件名> <一句话问题类型>

受影响：<包名> <版本范围>
文件与位置：<路径> 第 <行> 行
问题类型：<例：硬编码凭据 / 远程拉取执行 / 越权读取用户目录>
影响：<不修会怎样，一两句>
参考：<CWE 编号 / MITRE ATT&CK 编号>
建议修法：<一句话>
披露时间线：我计划在 90 天后（YYYY-MM-DD）公开，若你们需要更多时间请告知。
```
- 审查报告里的**文件路径 + 行号 + 规则 + 权威依据**直接够用。
- **不附复现脚本、不附利用代码**。维护者看路径和行号就能懂；懂不了会问你。
- 密钥、令牌：只说"第 N 行存在疑似 XX 令牌"，**不粘值**。

### 第 3 步：等待与跟进
- 行业惯例：**90 天**披露窗口（Google Project Zero 起的头，多数厂商接受）。
- 7 天没回复 → 再发一次；14 天没回复 → 换渠道（issue 里要联系方式）。
- 对方修了 → 确认版本号，等他们发公告后你再公开。
- 到期不修、不回 → 你可以公开，但**依然只公开事实与影响，不公开利用方法**。

### 第 4 步：CVE（可选）
CVE 是漏洞的全球唯一编号，方便大家引用。
- 大项目通常自己申请（GitHub advisory 里有"Request CVE"按钮，维护者点）。
- 你自己申请：[cve.mitre.org 表单](https://cveform.mitre.org/)，选 "Report Vulnerability/Request CVE ID"。
- **不是每个问题都值得 CVE**：只有"别人也在用、会被影响"的才申请。你自己项目里的配置错误不用。

## 三、大厂产品（C 类）

| 厂商 | 渠道 | 备注 |
|---|---|---|
| 微软（Windows、VS Code、Edge、Azure、GitHub 平台本体） | [MSRC 研究者门户](https://msrc.microsoft.com/report/vulnerability) | 注册 → 填表；有赏金计划；中文可以，但英文处理更快 |
| GitHub（平台功能，非某个仓库） | [HackerOne GitHub 项目](https://hackerone.com/github) | 仓库里的代码问题不归这里，归仓库维护者 |
| 苹果 | [Apple Security Research](https://security.apple.com/) | 需要 Apple ID |
| 谷歌（Chrome、Android、Google 服务） | [Google Bug Hunters](https://bughunters.google.com/) | Chrome 走 [crbug.com](https://crbug.com) 选 Security 模板 |
| Cloudflare | [HackerOne Cloudflare 项目](https://hackerone.com/cloudflare) | |
| 中国境内厂商 | 优先厂商自己的 SRC（如 阿里 ASRC、腾讯 TSRC、百度 BSRC）；通用平台 [CNVD](https://www.cnvd.org.cn/)、[CNNVD](https://www.cnnvd.org.cn/) | |
| 开源基础设施（npm 包、PyPI 包本体的恶意） | npm：[报告恶意包](https://www.npmjs.com/support)；PyPI：security@pypi.org 或包页面 "Report project as malware" | 恶意包**不需要**给维护者 90 天——直接报平台下架 |

### 填表时的常见归类（英文表单怎么选）
| 你看到的 | 表单里选 | 对应 CWE |
|---|---|---|
| 硬编码密钥/令牌 | Information Disclosure / Sensitive Data Exposure | CWE-798、CWE-312 |
| `curl … \| sh`、下载后执行 | Remote Code Execution / Supply Chain | CWE-494、CWE-829 |
| `eval`/`exec` 处理不可信输入 | Code Injection | CWE-94、CWE-95 |
| 偷读 `~/.ssh`、浏览器密码库 | Information Disclosure / Privacy Violation | CWE-200、CWE-359 |
| 定时任务/服务/注册表自启 | Persistence（表单没有就选 Other + 说明） | ATT&CK T1053 / T1543 / T1547 |
| 改 hosts / 代理 / 浏览器策略 | Man-in-the-Middle / Tampering | CWE-350、ATT&CK T1557 |
| AI 配置文件里的隐藏指令 | Prompt Injection（新分类，多数表单选 Other） | OWASP LLM01 |
| 依赖钉死到个人 fork / 陌生 registry | Supply Chain / Dependency Confusion | CWE-829、CWE-1104 |

## 四、中文用户容易踩的坑

1. **编码**：表单和邮件用 UTF-8；粘贴路径时确认没被改成全角字符（`：` vs `:`、`／` vs `/`）。Windows 路径里的反斜杠在 Markdown 里要写两个 `\\`。
2. **语言**：多数国际渠道英文处理更快。可以中英双语：中文写清楚，再附一段简短英文摘要（问题类型 + 位置 + 影响即可，不需要好文笔）。
3. **时间**：写日期用 `YYYY-MM-DD`，时区写 `UTC+8`。
4. **截图**：路径和行号用文字，不要只发截图（他们要搜索、要复制）。截图里**不要出现密钥值**。
5. **不要威胁**："不修我就公开"是常态流程（90 天），但语气要平铺直叙——写日期，不写情绪。
6. **不要要钱**：先报告，赏金由厂商按规则给。开口要钱在很多司法辖区会被视为勒索。

## 五、哪些事**不要做**

- **不要**验证漏洞是否"真的能用"——在别人的系统上试就是入侵，哪怕你是好意。
- **不要**把利用代码、复现脚本发给任何人（包括维护者，除非他们明确要求且渠道私密）。
- **不要**在公开场合贴密钥值、内网地址、用户数据，哪怕"打了码"。
- **不要**替别人决定"这没事"。你能做的是如实报；严重程度由维护者和 CVE 评分定。
- **不要**在对方修好前公开细节。

## 六、跟审查报告怎么配合

审查报告（`<仓库名>.md`）里每条发现都有：文件路径、行号、规则 ID、风险名称、后果、权威依据。写上报时：
- 把这几项**原样抄**进"文件与位置""问题类型""参考"。
- 代码行**不要抄**（尤其 `严重` 级和 `必须删除` 的），路径+行号足够。
- 报告里的"处置"（必须删除/必须修复/建议修复）可以作为你对"建议修法"的依据。
